# 개념 헌장 (Concept Charter) — @rchemist/listgrid

**작성**: 2026-07-10 · **Status**: active — 재기초(ADR-0008)의 스코프 울타리이자 0.4.0 GA 게이트의 대조표
**성격**: 이 문서는 **구현과 무관하게 보존되는 개념의 명세**다. 코드·API 형태·파일 구조는 전부 재량이지만, 아래 C1~C9가 깨지면 그것은 리팩터링이 아니라 **다른 제품**이다. 사용자 원칙: *"개념만 흡수하고 코드는 전면 폐기해도 좋다 — 단 개념은 모두 유지된다."*
현행 코드(v0.3.x)는 이 헌장의 **레퍼런스 구현**이다: 명세가 모호하면 현행 동작 + 특성화 테스트(P2)가 판정 기준이다.

---

## C1. 선언 = 화면

엔티티 하나를 **한 곳에서 선언**하면(필드·정책·관계 포함) 리스트 화면과 폼 화면이 **둘 다** 파생된다. 리스트용 컬럼 정의와 폼용 필드 정의를 따로 쓰게 만드는 순간 이 개념은 깨진다.

```ts
const userForm = new EntityForm('user', '/api/users').addFields({ items: [
  new StringField('name', 1).withRequired(true),
  new ManyToOneField('department', 2, ...),
]});
// → <ViewListGrid listGrid={new ListGrid(userForm)} />  와
// → <ViewEntityForm entityForm={userForm.clone().withId(id)} />  가 모두 이 선언에서 나온다
```

체이너블 빌더 문법(`withXxx`)은 이 선언의 문법이다 — 이름 규칙의 일관성 자체가 학습 곡선을 낮추는 자산이므로 유지한다.

## C2. 정책은 코드가 아니라 데이터다

hidden / readonly / required / 권한 / 수정가능성은 **조건부 선언**이며, 조건은 폼 상태(렌더 타입 create/update, 다른 필드 값, 세션)의 함수다. 소비자가 if문 분기로 화면을 짜게 만들면 깨진다. 대표 어휘: `ALWAYS`/`HIDDEN`/`VIEW_ONLY`/`MODIFY_ONLY`/`HAS_VALUE_READONLY`/`ADD_ONLY`, `withRequiredPermissions(...)`, conditional 함수형 값(`ConditionalBooleanValue` 등).

## C3. 관계는 1급이다

이 엔진의 결정적 차별점. 외부 참조가 "id 텍스트박스"로 퇴화하면 안 된다.

- **ManyToOne**: 검색 가능한 참조 선택 + **참조 대상의 조회/생성/수정 팝업**(팝업 안은 그 엔티티의 완전한 폼) + 필터 연동 + 트리 뷰.
- **OneToMany / ManyToMany (SubCollection)**: 부모 폼 안에서 자식 컬렉션을 **인라인/테이블/카드**로 조회·생성·수정·삭제. `mappedBy` 기반 자동 필터. 중첩(자식의 자식) 재진입 허용 — 단 깊이 제어 장치 포함.
- 부모↔자식 상태는 **격리**되고 통신은 명시적 프로토콜(콜백/캐시 전달)로만 한다 — 현행 구조의 검증된 강점.

## C4. 필드 카탈로그와 그 미시 결정

40+ 필드 타입(문자/숫자/날짜 계열/선택 계열/파일·이미지/주소·지도/전화/색상/HTML·Markdown/QR/규칙 기반 등)이 **폼 입력·리스트 셀·필터·엑셀 왕복·검증**의 5개 문맥을 스스로 안다. 그리고 각 필드에 축적된 **미시 결정 — dirty 판정의 빈값 정규화, 날짜 범위의 관용적 파싱, `0`과 null의 구분, 한국 전화/주소 체계 —** 은 문서에 없고 코드에만 있는 개념의 일부다. 따라서 재기초에서 필드 로직은 **재작성이 아니라 이식**한다(ADR-0008 규율 2). 신규 필드 타입 추가는 "클래스 1개 + 렌더러 1개 등록"으로 닫혀야 한다.

## C5. 검증·연쇄 모델

- 검증은 필드에 **선언**한다(12종 + 커스텀 + 조건부 검증). 실행 시점: 변경 시 해당 필드 스코프, 저장 시 전체.
- `onChange` 연쇄: 한 필드의 변경이 폼 수준 로직(다른 필드 값/표시 상태 변경)을 선언적으로 트리거한다(`OnChangeEntityForm`).
- 오류는 필드 단위로 귀속·표시되고 폼 수준으로 병합된다. 서버 검증 오류도 같은 채널로 필드에 매핑된다.

## C6. 폼 구조화 요소

탭 / 필드그룹 / 생성 스텝(위저드) / 자동저장(이탈 복구) / 리비전 히스토리(변경 이력 보기) / 엑셀 import·export(필드 선언에서 컬럼 매핑 파생, 왕복 무손실). 이들은 전부 **필드 선언 위에 얹히는 선언**이지 별도 화면 코드가 아니다.

## C7. 엔진은 아무것도 소유하지 않는다

UI 프리미티브·라우터·URL 상태·세션·HTTP 전송·메시지(토스트/컨펌)·i18n은 전부 **호스트 주입**이다. 엔진은 특정 메타프레임워크·UI킷·상태 라이브러리를 소비자에게 강제하지 않는다. 미주입 시의 기본 동작은 "조용한 이상 동작"이 아니라 **문서화된 폴백 + 경고**여야 한다(0.3.x의 fail-open 침묵은 헌장 위반 사례였다). schema-core와 상태 계층은 React 0%를 유지한다 — 이것이 장기적으로 위젯 빌드/웹 컴포넌트(다른 프론트 기술) 확장의 문을 여는 조건이다.

## C8. 백엔드 관례는 어댑터다

CRUD URL 조립·응답 해석·오류 의미(`TOKEN_EXPIRED` 등)는 `BackendAdapter` 계약 뒤에 산다. **RCM-framework는 1급 기본 어댑터**로 최상의 경험을 제공하고, 다른 백엔드는 어댑터 1개 구현으로 연결된다(in-out). 관례가 엔진 코어에 하드와이어되면 헌장 위반이다(0.3.x의 상태가 그랬다).

## C9. 리스트 상호작용 표준 세트

리스트 화면은 페이지네이션·다중 정렬·퀵서치·고급 검색·필터·컬럼 선택·행 선택/일괄 작업·URL 상태 동기화(공유 가능한 화면 상태)·행 액션을 **기본 내장**한다. "허접한 CRUD 엔진"과의 경계선이 바로 이 세트다 — 어느 하나도 소비자 구현 몫으로 밀어내지 않는다.

## 비개념 (구현 재량 — 보존 의무 없음)

클래스 상속 구조(5단 mixin), 상태 라이브러리 선택(zustand 여부), `EntityForm` 인스턴스가 런타임 상태를 직접 보관하는 방식, 파일/패키지 배치, CSS 구현 세부, 전역 싱글턴 방식, `.tsx` 확장자. — 전부 ADR-0002/0003/0008에 따라 교체된다.

## 보존 검증 (0.4.0 GA 게이트)

1. **특성화 테스트**(P2)가 신 엔진에서 동일 통과 — C4·C5의 미시 결정 보존 증명
2. **헌장 대조표**: C1~C9 각각에 대해 "신 엔진에서의 구현 위치 + 시연 시나리오(examples/minimal)" 1행씩 작성 — 빈 행이 있으면 GA 불가
3. 사용자 시나리오 재현: 원 호스트(GJCU/edustack)급 실제 엔티티 1종을 신 엔진 선언으로 재작성해 리스트+폼+관계+엑셀이 동작함을 확인
