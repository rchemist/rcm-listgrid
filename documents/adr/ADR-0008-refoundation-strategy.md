# ADR-0008 — 실행 전략: 재기초(re-foundation) + 장기 이식

**Status**: accepted (사용자 확정, 2026-07-10) · **Date**: 2026-07-10
**관계**: ADR-0001~0007의 **목적지(아키텍처 결정)는 전부 유지**된다. 본 ADR은 그 목적지에 도달하는 **경로와 릴리스 창구 배치**를 결정하며, 각 ADR 본문의 "0.4.0/0.5.0 창구" 언급은 본 ADR의 버전 계획이 우선한다.
**근거**: 사용자 목표 재확인 — "개념만 흡수하고 코드는 전면 폐기해도 좋다. EntityForm 모델링·정책 선언·관계 필드 등 개념이 모두 유지되는 엔터프라이즈급 엔진이 목표" + [개념 헌장](../prd/concept-charter.md)

## Context

두 실행 전략이 있었다:

- **A. 제자리(in-place) 순차 재설계** — 살아있는 트리에서 P3(표면)→P4(계약)→P5(상태)→P6(어댑터)를 차례로 통과. 매 단계 출하 가능하나, 아키텍처 3축이 **같은 핵심 파일(EntityForm/FieldRenderer/useEntityFormLogic)을 3번 열어 3번 재배선**하는 중복 비용을 낸다.
- **B. 재기초 + 장기 이식** — 워크스페이스에 4계층 골격(ADR-0003의 목표 아키텍처)을 처음부터 **최종 형태로 신축**하고, 검증된 로직(필드/검증/SearchForm/CSS)을 특성화 테스트 오라클 아래 이식한다.

B를 여는 조건이 모두 성립한다: ① 공개 표면은 어차피 breaking(ADR-0004), ② 프로덕션 소비자 2계열이 전부 유지보수자 통제 하, ③ 사용자가 명시적으로 코드 폐기를 허용, ④ 원하는 결과물이 "고쳐진 0.3"이 아니라 "개념이 제대로 서 있는 엔진".

## Decision

**전략 B를 채택한다.** 단, "폐기"의 대상을 엄격히 한정한다:

- **신축(폐기 후 재작성)**: 상태 전파 배선, config↔render 계약, 전역 싱글턴 구조, 패키징, EntityForm 5단 상속 — 아키텍처 3축 전부
- **이식(보존)**: 필드별 렌더/검증/포맷 로직(17.9k LOC의 미시 결정), SearchForm 직렬화, CSS 디자인 시스템, 관계 편집 UX — **개념은 API 모양만이 아니라 코드에 축적된 엣지케이스에 산다**. 백지 재작성은 이를 수년치 프로덕션 버그로 재지불하는 경로라 기각.

### 워크스페이스 구조 (npm workspaces 모노레포)

```
packages/
  schema-core/    # EntityForm 선언·필드 메타·검증·SearchForm·PermissionPolicy — React 0% (lint 강제)
  state/          # createFormStore/createListStore — zustand vanilla, 프레임워크 무관
  react/          # 렌더러: 필드 렌더러 레지스트리 + 40종, ViewEntityForm/ViewListGrid, 테마
  ui-default/     # 스타일드 프리미티브 (headlessui/react-select/sortablejs peer 격리)
  backend-rcm/    # BackendAdapter 구현 (rcm-framework 0.1.0, 1급 기본)
  backend-rest/   # generic REST 레퍼런스
  presets-rcm/    # 원 호스트 도메인 프리셋 (색상맵·MarketingField 등)
  next/           # Next.js 어댑터
```

**배포 형태**: 당분간 단일 `@rchemist/listgrid` 패키지 + 서브패스 exports(워크스페이스 빌드를 매핑). 멀티 패키지 분리는 실수요(예: schema-core 단독 소비) 확인 후. 프레임워크 확장(위젯 빌드/웹 컴포넌트)은 schema-core+state의 React 0% 규율이 열어두는 **옵션**이며 v1 스코프가 아니다.

### 버전·브랜치 계획 (사용자 확정, 2026-07-10)

| 라인 | 브랜치 | 내용 |
|---|---|---|
| 0.2.x | `release/0.2` (기존) | 유지보수 (기존 관례 그대로) |
| 0.3.x | `main` (현행 유지) | 유지보수 전용 — P0 핫픽스 = 0.3.26. BREAKING 금지 |
| **0.4.x** | **`v0.4` (신설, main에서 분기)** | **재기초 엔진의 개발·착지 라인.** ADR-0001 패키징(tsup dual)이 이 워크스페이스의 빌드 기반. 개발 중에는 `0.4.0-alpha.N`을 npm dist-tag `next`로 상시 배포(암흑기 통제 — §방지 장치 5). parity + 헌장 대조 통과 시 0.4.0 GA |
| 1.0.0 | — | 새 기능이 아니라 **표면 동결 선언**. 0.4.x가 프로덕션에서 구워지고 PRD §5의 안정화 기준(외부 채택·커버리지 40%·로드 스모크 매트릭스 등)을 충족하면 그 시점의 0.x를 1.0으로 승격 |

**0.4 GA 시점의 브랜치 플립**: `main`의 0.3.x는 `release/0.3`로 이관하고(release/0.2 선례와 정합) `v0.4`를 main으로 승격한다. 그전까지 CI는 main·v0.4 양쪽에서 돈다. 워크스페이스 재편으로 v0.4↔main은 사실상 merge 불가능한 발산이므로, 플립은 병합이 아니라 승격(기본 브랜치 전환)으로 처리한다.

(구 계획의 "0.4 표면 재단 → 0.5 코어 재설계 → 1.0 착지"는 폐기 — 옛 배럴을 재단하고 새 엔진에서 또 재단하는 이중 작업 제거. 0.3.x 소비자에게 패키징 픽스가 GA 전에 급히 필요해지면 tsup 구성만 main에 백포트하는 옵션을 열어둔다.)

## 2차 시스템 효과 방지 장치 (전부 강제 규율)

1. **헌장 = 스코프 울타리**: v1은 [개념 헌장](../prd/concept-charter.md)의 개념만 이식한다. 이식 중 떠오르는 신기능·개선 아이디어는 backlog로 보내고 v1에 넣지 않는다.
2. **이식 우선, 재발명 금지**: 리프 로직(필드/검증/포맷)은 테스트와 함께 **옮긴다**. 리프를 다시 쓰려면 해당 PR에 사유 노트를 남겨야 한다.
3. **특성화 오라클**: P2의 테스트 그물이 신구 양쪽에서 동일하게 통과해야 이식 완료로 친다.
4. **이식 중 동시 처리는 고정 목록만**: i18n 키화, 중복 통합(3중복 권한·SubCollection 3변형·misc/utils), `any` 제거, 도메인 리터럴 격리, a11y 3종(ADR-0006). 이 목록 밖의 "하는 김에" 변경 금지 — 필요하면 새 ADR.
5. **암흑기 통제**: `v0.4` 브랜치에서 `0.4.0-alpha.N`을 npm dist-tag `next`로 상시 배포하고, `examples/minimal`을 이식과 함께 자라는 통합 데모로 운영한다 — "돌아가는 알파"가 없으면 그 달은 진행이 없는 것으로 간주한다. 0.3.x 라인이 소비자를 막지 않는다.
6. **중단 기준(abort)**: P4(코어 이식)가 추정치의 150%를 초과하거나 parity가 반복 실패하면 전략 A로 회귀한다 — 이때 P3에서 만든 골격은 A의 P4~P5 목적지로 그대로 쓰이므로 매몰 비용이 아니다.

## Consequences

- 로드맵의 P1 이후가 재기초 페이즈로 재편된다 → [plans/v1-roadmap.md](../plans/v1-roadmap.md) 개정.
- MIGRATION은 "0.3 → 0.4" 단일 대이동 문서 + codemod가 된다 (다단계 breaking 대신 1회).
- 0.4.0 GA 게이트에 **헌장 대조**(개념 C1~C9 보존 확인)가 추가된다.
- 0.3.x 지원 정책: 0.4.0 GA 후 6개월간 보안·치명 버그만 백포트(main→release/0.3), 이후 EOL 고지.
